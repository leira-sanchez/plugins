### Bug fix

**Own the reproduction, root cause, and proof.** A report in the current conversation is enough. Use the [Codex runtime contract](../references/codex-runtime.md) for available tools, delegation, and authorization. Delegate scoped investigation or implementation when useful and permitted; otherwise run the same phases yourself.

Every shipped line traces to evidence. A change that "might help" is a hypothesis. When evidence refutes it, revert that experiment without discarding unrelated work.

1. **Triage the report.** Read the supplied steps, attachments, and logs. Identify the expected behavior, observed symptom, trigger, affected version/environment, frequency, and exact state where correct and broken behavior diverge. Use `how` to trace the affected path and `why` for regression history. Distinguish a defect from an intentional behavior or feature request; if intent is unclear, investigate before assuming a fix. Check relevant local history and supplied PRs or commits for an existing fix. Use a tracker only when available and relevant; do not create tickets or send messages just to run this workflow. If a concrete fix exists, follow [Verify an existing fix](../references/verify-existing-fix.md) and return its verdict. If the user wants diagnosis or reproduction only, honor that scope.
2. **Prepare a bounded run.** Read the project's verification skill and matching feature-map entry, if present. For an unmapped feature, inspect the app and derive a scoped user-path recipe. Use the [control-adapter contract](../../create-verification-skill/references/control-adapter.md) for environment, reset, evidence, and cleanup requirements. Record the app revision, disposable fixtures, starting state, artifact location, and time or attempt limit. Check required capabilities before starting. At the limit, report findings and a next step rather than looping indefinitely.
3. **Reproduce the exact symptom.** Drive the reported path yourself through the actual UI, CLI, or API. Confirm app identity and the discriminating broken state. For a repeatable defect, reset and reproduce twice; capture the actions and result, plus a read-only state cross-check when available. Arrange preconditions through fixtures or supported test controls, but never inject the symptom with internal setters, storage writes, or DOM mutation. For an intermittent or performance issue, record attempts and measurements and define a comparison criterion. Do not manufacture confidence from two samples. If a required capability is absent, report **Blocked**; if the run completes without the symptom, report **Could not reproduce**. Neither outcome authorizes a speculative fix. Ask the user to reproduce only after explaining the specific part of the surface you could not reach.
4. **Prove the cause and plan the fix.** Form competing hypotheses and use runtime evidence to eliminate them. Instrument temporarily when program state is unclear. Confirm the surviving mechanism before changing behavior. If the fix crosses function boundaries, use `architect` for its design. Keep the change within the requested scope and work budget. An existing patch switches the task to verification rather than parallel implementation.
5. **Implement the smallest justified fix.** Use `tdd` when a cheap local test can demonstrate the failure: run that test red before editing production behavior, then make it green. When a test would require brittle mocks or disproportionate setup, explain the choice and preserve the executable reproduction instead. Delegate to a scoped worker only when available and permitted, using the configured bug-fix model (default `inherit-parent`). Review its diff and evidence before accepting it.
6. **Repeat the original proof on the patched build.** Use the same user path, fixtures, and observation rules as the baseline, reset between attempts, and demonstrate both the disappearance of the defect and the expected result. For repeatable bugs, repeat twice; for intermittent or performance bugs, use the criterion fixed in step 3. Review the evidence to ensure it shows the final discriminating state, not merely setup or loading. Run focused regression checks and nearby behaviors affected by the change. A compile, green unit test, wrong-surface check, or inconclusive result is not proof that the reported bug is fixed.
7. **Deliver within scope and clean up.** Return the verified local diff and evidence when that is the requested outcome. When commits are part of the task, keep the failing test before the fix in ordered history where practical. Run **Opening a PR** only when requested or already authorized; a PR for this workflow should include repro steps, cause, checks, and before-and-after proof. Do not merge or deploy as part of a bug fix. On every exit, stop resources created for the run and restore disposable fixtures while preserving user work and evidence. Keep captures, recordings, credentials, and debug logs out of commits by default.

**Reply:** outcome, what was broken, root cause if established, what changed, exact verification steps and evidence, and any remaining gaps. Show concise failing-then-passing output when applicable. For UI defects, point to the before-and-after captures or recording. Diagnosis-only and unsuccessful runs return findings without a patch or PR.
